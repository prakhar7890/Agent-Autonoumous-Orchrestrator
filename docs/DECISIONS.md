# Binding Decisions

These decisions resolve implementation details for the project and are binding for
the prototype. They supplement the original requirements in [SPEC.md](./SPEC.md).

## Runtime and graph backend

- Use a Python 3.12 virtual environment for development and verification.
- Neo4j AuraDB Free is the verified graph backend. `deploy/optional/docker-compose.yml`
  is an unverified, optional local alternative and must not be described as verified.

## Configuration

- `Settings` rejects an `AGENT_REPO_HASH_SALT` that starts with `change-me` (the
  `.env.example` placeholder), so copying the template without editing a real salt
  fails fast. The test suite supplies its own fixed test salt (`tests/conftest.py`)
  and never depends on a developer's `.env`.

## Cases and breakpoints

- Automatic cases support both exact-field checks and “must not contain” checks.
- Feedback is limited to 10 submissions per identified user in a rolling hour by
  default; the limit is configurable on the feedback service.
- Negative feedback requires a substantive comment of at least 8 characters; common
  placeholder comments are rejected.
- Demo breakpoints must be produced by real runtime conditions; do not fabricate
  breakpoint results solely for demonstration.

## Routing and evaluation

- Select a workflow's goal agent only by scoring request terms against stored agent
  metadata. Do not add an intent-to-output table or hardcoded per-query routing.
- A candidate passes evaluation only when accuracy strictly improves, no previously
  passing case regresses, and latency and token budgets hold.
- With no evaluation cases, mark the proposal `needs_cases`; never auto-promote it.

## LLM rewrite and demonstration

- The demo includes a scripted rewrite explicitly labelled `MOCK LLM`.
- The demo also includes one rewrite rejected by the evaluation gate.
- Treat every rewrite as untrusted input; it may change only `system_prompt` and
  `pipeline`, and must be validated before a candidate version is created.

## Governance and command-line interface

- “Human approver” is a naming convention, not authentication.
- Use Python's `argparse` only for command-line parsing; do not add another CLI
  framework.
- The M5 CLI uses `--graph-file` for JSON-persisted memory storage; otherwise it
  uses Aura when `NEO4J_URI` is configured, and ephemeral memory when it is not.
- CLI rewrites use the deterministic `MockLLM` offline by default. A proposal
  rewrite can be supplied explicitly as JSON; no credential or test-wipe option
  is exposed in the CLI.
- The ordered demo writes to the selected graph. Use a fresh graph file for a
  repeatable clean run; the demo (and the automated tests) still use the
  deterministic stubs for audio, image, image-generation, and email. Real ASR and
  vision are opt-in only (see "Real tool integrations" below).

## Documentation (Milestone 6)

- Every M6 document is written from the code and from real command output; no
  capability is claimed that was not run. Unrun paths (Docker, live LLM providers)
  are labelled "not verified".
- `docs/AGENT_CATALOG.md` is generated by `agent-repo catalog` and is **deterministic** for a
  given repository state (agent metadata only). `docs/graph_export.cypher` and
  `docs/graph_export_after_demo.cypher` are generated by `agent-repo cypher --output` and are
  **not deterministic**: they contain freshly generated node/relationship ids and creation
  timestamps, so two exports of the same logical graph differ byte-for-byte. `docs/queries.cypher`
  stays a hand-written set of named "useful queries" (the CLI cannot generate named queries).
- The M6 docs state plainly that the human approver is a naming convention (not
  authentication), that the `MockLLM` path is the only one exercised by this project's
  automated tests and demo, that free text is scrubbed
  at write time while exports keep stored ids/hashes, and that regex scrubbing cannot
  catch names or free-form personal data and may over-redact phone-like numbers. Live
  provider calls are reported separately in [`docs/LLM_PROVIDERS.md`](./LLM_PROVIDERS.md).

## Dependency pinning

- `langgraph` and `langgraph-checkpoint` are pinned in `pyproject.toml` to the exact
  versions installed and verified in this environment (`langgraph==1.2.15`,
  `langgraph-checkpoint==4.3.0`) rather than a floating `>=0.2`. The engine and the
  `MemorySaver` checkpointer behaviour (including the "deserializing unregistered type"
  warnings) are specific to these versions, so pinning keeps behaviour reproducible.

## Live LLM providers (Milestone 7)

- Live model ids are **inputs** to `make_llm("provider:model")`, never constants in code, because
  provider model availability drifts. The models verified live on 2026-10-19 were
  `gemini:gemini-3.5-flash` and `groq:openai/gpt-oss-20b`; the historical names in SPEC/early docs
  (`gemini-1.5-flash`, `llama-3.1-8b-instant`, …) are retired or not accessible to this key.
- The live provider adapters are pinned in the `providers` optional extra
  (`langchain-google-genai==4.4.2`, `langchain-groq==1.1.3`, `langchain-openai==1.7.2`,
  `pip install -e ".[providers]"`). The base install stays offline-only (`MockLLM`); the automated
  tests still never call a live provider.
- The OpenAI provider path is **not verified**: the account has no credits (HTTP 429
  `insufficient_quota`). This is a billing state, not a code defect.
- Providers that return structured content blocks (Gemini 3.x) are normalised to plain text by
  `extract_text()` in `agent_repo/llm.py`, which `LangChainLLM.generate` calls. Only readable text
  is kept; non-text blocks and provider signatures are dropped, and `draft_agent` inherits the
  normalisation. Verified live (`gemini:gemini-3.5-flash` now returns the plain string `READY`) and
  covered offline by `tests/test_llm_text_extraction.py`.

## Real tool integrations

- Only `audio_transcribe` and `image_classify` have real implementations for now, and they are
  **opt-in** via `ToolSettings` (`AGENT_REPO_TRANSCRIBER=groq`, `AGENT_REPO_IMAGE_CLASSIFIER=gemini`).
  The **stubs stay the default** so the offline test suite and the recorded demo remain deterministic
  (spec §2: a stub must never be presented as real capability). `image_generate` and `email_send`
  remain stubs with no real implementation.
- Providers were chosen from the keys already verified live: Groq `whisper-large-v3` for ASR and the
  Gemini vision model `gemini-3.5-flash`. As with LLM model ids, the model is an input/override, not
  a hardcoded constant.
- A real tool's output is never labelled `stub`; provider failures raise `ToolError` (retryable) and
  missing keys raise `ToolError` with the env-var name only — **keys are never logged or echoed**.
- The provider client builders are module-level functions so tests substitute a fake client and never
  touch the network. Live verification evidence (real synthesized speech, a generated image) is in
  [`TOOL_INTEGRATIONS.md`](./TOOL_INTEGRATIONS.md).
